## Problem, restated

Everything for 3D lessons exists, but nothing in the product asks for one:

- The planner's system prompt (`PlannerPrompt.System`) only describes schema `heyganesh.visualplan/1`, card surfaces and
  the v1 ops. A model has never been told that `scene3d`, `model`, `label`, `explode`, `animate` or `camera` exist, or
  which models, parts and animations it may name. So even with a catalogue it would never plan 3D.
- The App Shell's `--lesson` leg builds its `PlanRequest` without `Scene3d`, so the validator refuses any 3D plan, and it
  calls `LessonTurn.RunAsync`, so a clicked part goes nowhere.

These are two logical changes with different risks and different tests, so I propose doing them in order, one approval
each:

1. **6a. Teach the planner.** Prompt only, verified offline in LessonPlannerSmoke. No product behaviour changes, because
   no product caller passes a catalogue yet.
2. **6b. Turn it on in the shell.** `--lesson` passes `CardSurface.Scene3dCatalog` and calls `RunWithFollowUpsAsync`.
   This is the first change a real user can see, and its live path needs `DEEPSEEK_API_KEY`.

### Execution path

`VisualPlanner.PlanAsync` → `PlannerPrompt.System(limits, request.Scene3d)` + `PlannerPrompt.User(...)` → model →
`VisualPlanValidator.Validate(..., context { Scene3d = request.Scene3d })` → repair turn with the issues if needed
(unchanged). Documented in FLOW under the planner section; the only new edge is "prompt depends on `request.Scene3d`".

### Alternatives considered

- **Add titles and descriptions to `CatalogModel`, so the model also sees "Connecting rod: links the piston to the
  crankshaft…".** Better grounding, but it changes the VisualPlan contract type (DEC-028 keeps the catalogue names-only)
  and makes the prompt about 3× longer. Rejected for v1: the ids are readable English (`connecting-rod`,
  `valve-intake`). It's a good follow-up once a live run shows whether the model mislabels parts.
- **Always describe 3D in the prompt, whether or not a catalogue is passed.** Rejected: a caller whose canvas can't draw
  3D would get plans that all degrade to speech. The prompt should offer exactly what the validator will accept, which
  is the rule this file already states.
- **A separate 3D planner.** Rejected: one lesson mixes a scene and cards, as the engine fixture does.

### What could break, and how we'd know

- **The existing 2D prompt changes by accident.** LP-1..LP-8 rerun unchanged, plus a new row checks the no-catalogue
  prompt contains no `1.1`, `scene3d` or 3D op names.
- **The prompt drifts from the validator** (an op shape the parser doesn't take). Rows feed every documented 3D op back
  through the real parser and validator. Names come from code (catalogue, `CameraView`, `LessonLimits`), never typed by
  hand.
- **Prompt size and cost.** With the 3-model catalogue the system prompt grows by roughly 600–900 tokens. Printed by the
  row. It only applies when 3D is on.
- **The real model may still plan badly** (wrong part, no scene when one would help, too many ops). Only a live run
  shows that, and it is NOT verifiable without `DEEPSEEK_API_KEY` (LP-8, the live planner row, is still pending).

**Decision for you (6b): what does Ctrl+Alt do while a finished 3D lesson waits for a click?** Today any press during a
lesson is refused ("one Ctrl+Alt hold maps to one turn").

- *Recommended for v1:* keep refusing, with a clearer message ("close the 3D lesson (×) or wait up to 30 s to ask by
  voice"), and use a 30 s idle instead of 60 s. No new shell state.
- *Alternative:* a press during the wait closes the lesson and starts the new voice turn. Better for a demo, but it adds
  a phase to the shell's turn state machine, and the shell has no fakes to test that offline (DEC-012).

**6b verification:** SH-18 (no key → skip line, exit 12) and every SH offline row unchanged. The live 3D turn is
human-gated: it needs `DEEPSEEK_API_KEY`, `TYPESAFE_API_KEY`, the Gateway and a mic. NOT verifiable here today.
